# E-14 demo fixtures

Generated by `cargo xtask gen-demo`. Every file here is hashed in `MANIFEST.sha256`, and the
demo refuses to run when a hash has moved, so a scene cannot be tuned by editing a fixture.

## The signing key

qp_key is the public half of RFC 8032 §7.1's TEST 1 key, whose private half that document publishes. It stands for no qualified person and credentials nobody (RES-04).

## The identifiers

The tenure identifier, jurisdiction and registry code are synthetic. DEMO0000 is not a registry. The canonical tenure is `DEMOTENURE0001X`, from the raw spelling `demo-tenure 0001-x`, under
jurisdiction `CABC` and registry `DEMO0000`.

## The epoch key

master_key is published here so the page can build epochs live. In a deployment the epoch key never leaves the batcher (INV-STATE-03, RES-03).

## Why the packages carry no notes of their own

§2.5 fixes what a disclosure package contains and INV-DISC-01 makes that list closed. A
conforming verifier refuses the first field the section does not list, so a note added to
`disclosure.json` would make it unverifiable. The labels are therefore here, in a file the
manifest covers, rather than inside the packages.

## What each file is

- `disclosure.json` — a §2.5 package for the third record of a three-record chain. Past
  `seq` 1 nothing in a package pins `prev_head`, so a verifier reports the chain position as not
  established. The demo shows that line rather than shipping a `seq` 1 package that avoids it.
- `tampered.json` — the same package with the low bit of `payload_digest` flipped: byte
  48 of the preimage, and the hex the JSON displays beside it. The two halves still agree,
  so what refuses this package is the QP signature rather than an internal inconsistency.
- `root.json` — the epoch root a counterparty fetches from Solana, so the demo runs offline,
  with the chain's heads for display.

## The anchor block is a placeholder

This epoch was built for the demo and published nowhere, so `anchor.solana_tx`,
`anchor.solana_slot` and `anchor.ots_receipt_digest` are visibly empty values rather than a
real transaction. §2.5 carries that block and nothing in the section says how a verifier
checks it (SPEC-DEFECTS.md SD-12), so the verifier does not, and the page says so. The
announced log's own anchoring is real and is recorded in `docs/anchoring.md`; it does not
belong in a fixture whose root it does not anchor.
