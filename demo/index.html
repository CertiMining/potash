A log that shows the filing and hides the filer

Three scenes, computed in this browser. The epoch trees in Scene 1 are built as you move the control, and the verifier that checks the disclosure package in Scenes 2 and 3 is the same independent TypeScript implementation the repository ships — the verification happens here, now, and is not a recording of one. The package it verifies is synthetic: a committed fixture for an asset that does not exist, in an epoch published nowhere, generated by the engine rather than written by hand. The chain it describes is real in form and invented in content.

Scene one

The public view does not say how much you filed

Every epoch is a Merkle tree of fixed height 8 — 256 slots, always full, real submissions in pseudorandom slots and the rest padding under the epoch key. One record or two hundred and fifty-five, the chain sees one 32-byte root.

Move the count. The left column is one record and never changes; the right is whatever you choose. Everything except the record count is held fixed on purpose — the epoch, the slot, the timestamp and the receipt digest are all fields §4.4 permits to differ, so letting them move too would show two causes at once and prove neither. Those fixed values are synthetic: this epoch was built here and published nowhere.

Build time is wall-clock in your browser and is not something the chain shows. It is in the table because V-Z-01 varies it deliberately: a slower epoch must not land in a later slot, which is measured on devnet rather than here.

What this shows, and what it does not. It compares two artefacts — the CheckpointAccount and the publish_checkpoint instruction data — and shows that the record count moves no byte outside the closed list §4.4's V-Z-01 fixes, for the counts you try. It does not build a transaction. V-Z-01 also fixes the serialized transaction and its length, and a count-dependent byte in that wrapper would be invisible here while this page still reported a pass. That half is compared in programs/certimining-checkpoint/tests/privacy.rs, which runs against the real program under LiteSVM, builds the whole transaction, and treats any byte outside the list as a failure. The test is the authority; this is a demonstration. Count-hiding also rests on the padding being indistinguishable from real leaves, which is computational — an adversary who recovered the epoch key could tell them apart (RES-09) — and on the batcher keeping that key, which is a custody assumption, not a proof (RES-03). The key is published in this demo so the page can build epochs at all; in a deployment it never leaves the batcher.

Scene two

A counterparty verifies, offline, without asking anyone

A disclosure package is one record and its proof. The verifier recomputes the leaf from the signed bytes, checks the qualified person's signature over those bytes, and walks the proof to a root it obtained separately — here from fixtures/root.json, standing in for a fetch from Solana so that this runs offline.

The package's anchor block is not checked here and is a placeholder in this fixture: §2.5 carries that block and says nothing about how a verifier checks it, so this verifier does not pretend to. The announced log's own anchoring is real and is recorded in docs/anchoring.md; it does not belong in a fixture whose root it does not anchor.

Read the line that does not say “pass”. This package is the third record of its chain, and nothing in a package binds prev_head: §1.3's signed preimage does not cover it, and the proof binds only the leaf. So a verifier can confirm the record exists, unaltered, carrying the qualified person's signed statement of its position — and cannot confirm from this file alone that the position is the one it claims. The verifier says so rather than reporting a pass. A counterparty holding the previous head closes it; the demo ships the harder case on purpose.

Detection, not prevention. Nothing here stopped the alteration. What the architecture provides is that an altered record no longer matches what was committed, and that the commitment — the epoch root — did not move. On the announced log a published root is carried by a Solana slot and a Bitcoin block; this root is not, because this epoch was built for the demo and published nowhere, which is why the package's anchor block above is empty.

And what detection still leaves open. It says nothing about who made the change. It does not make the underlying estimate true: a log can show that a filing existed and was not edited afterwards, not that it was honest. Asset equivocation is the sharp one — an issuer can run two chains for the same tenure, disclose whichever suits a given counterparty, and both packages verify, because a counterparty holding one package cannot see the other. Nothing here prevents the same tenure being pledged twice, and nothing here asserts regulatory compliance.

Fixtures are generated by cargo xtask gen-demo and checked against fixtures/MANIFEST.sha256 before any scene runs. That catches a fixture edited after a clone; it does not catch one edited together with its manifest, because a manifest is as editable as the file it covers. What catches that is regeneration: CI runs the generator and diffs the result against the committed set, so a fixture the engine would not produce fails the build. Identifiers are synthetic and DEMO0000 is not a registry. The signing key is the public half of RFC 8032 §7.1's TEST 1 key, whose private half that document publishes: it stands for no qualified person and credentials nobody.
